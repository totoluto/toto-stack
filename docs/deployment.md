# Deployment

Apps generated by `create-toto-app` ship a production setup based on Docker Compose:
- MariaDB;
- a one-shot migration job;
- the app;
- Traefik for HTTPS with Let's Encrypt.

This page explains that setup and the requirements for any other deployment.

## Requirements for any deployment

- **Production mode.** Leave `NODE_ENV` unset or set it to `production`.
- **Required variables:** `SESSION_SECRET` (at least 32 random characters) and `ALLOWED_ORIGINS` (your public `https://` origin). Without them the server refuses to start and lists what is missing.
- **HTTPS** terminated by a reverse proxy, with `TRUST_PROXY` set to the number of proxies in front of the app. Otherwise the `Secure` session cookie is never set and logins don't stick. See [Security](security.md#tls-reverse-proxy-and-trust_proxy).
- **Migrations** applied with `prisma migrate deploy` before the new app version starts.
- **Secrets:** `SETUP_TOKEN` for the first-run setup, and `OTP_ENCRYPTION_KEY` if you encrypt TOTP secrets. Keep both, and the database credentials, in your secret store.
- **Shutdown:** a process manager that sends `SIGTERM` and waits long enough before killing the process. Draining requests and stopping cron jobs can each take up to `shutdown.timeoutMs` (10 s by default), so allow about 25 seconds, or lower the timeout.

## The template's Docker setup

```
docker-compose.yml            db (MariaDB), shared by development and production
docker-compose.override.yml   development only: DB port on 127.0.0.1, shadow-DB grant
docker-compose.prod.yml       migrate, app, proxy (Traefik)
Dockerfile                    multi-stage build: base, deps, build, prod-deps, migrate, runtime
```

**Requirements:** Docker Engine 20.10 or later and Docker Compose v2.1 or later (the `docker compose` plugin; `--wait` needs it).

Docker Compose loads `docker-compose.override.yml` automatically when no `-f` is given; that is the development setup (`docker compose up -d --wait db`). On a server, always pass both production files, or set `COMPOSE_FILE` in `.env`:

```bash
# .env on the server
COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml
```

The production files are split from the base file because Compose interpolates every service in the loaded files. If one file required `DOMAIN` and `ACME_EMAIL`, it would break `docker compose up db` in development.

### Services

| Service | Image | Role |
|---|---|---|
| `db` | `mariadb:11.8.9-noble` (LTS) | Database. Data lives in the `db_data` volume. Healthcheck: `healthcheck.sh --connect --innodb_initialized`. `MARIADB_AUTO_UPGRADE=1` upgrades system tables when the image changes. No port is published in production. |
| `migrate` | `migrate` build target | Runs `prisma migrate deploy` once, after `db` is healthy, then exits. |
| `app` | `runtime` build target | Runs `node dist/server.js` as the unprivileged `node` user, with `init: true` (tini as PID 1, so `SIGTERM` reaches Node). Starts only after `db` is healthy **and** `migrate` completed successfully. Listens on port 3000 inside the network; not published. |
| `proxy` | `traefik:v3.7.14` | Publishes ports 80 and 443, redirects HTTP to HTTPS, obtains certificates from Let's Encrypt (HTTP challenge) and compresses responses. Access log in `./logs/access.log`. |

### Images

| Stage | Contents |
|---|---|
| `base` | `FROM node:24.21.0-alpine3.24`. A literal tag (no build argument) so Dependabot can propose updates; change it here to use another Node version. |
| `deps` | Full dependency tree. The `postinstall` hook (`scripts/generate.js`) generates the Prisma client. `npm ci` if `package-lock.json` exists, otherwise `npm install` with a warning. |
| `build` | `npm run build`: Prisma client, then the Vite client, then the esbuild server bundle in `dist/server.js` (ESM, with the Prisma client bundled) and `dist/public`. |
| `prod-deps` | `npm ci --omit=dev --ignore-scripts`: only `toto-stack`, the MariaDB adapter and their dependencies. |
| `migrate` | `deps` plus the Prisma CLI, used only by the `migrate` service. |
| `runtime` (default) | `base` with `package.json`, production `node_modules` and `dist/`. Files are root-owned and read-only for the app user. `HEALTHCHECK` calls `GET /api/health`. |

The runtime image carries no Prisma CLI, schema engine, compiler or dev dependencies.

**Commit your npm lockfile.** It makes image builds reproducible. If you use pnpm, Yarn or Bun locally, still generate and commit a `package-lock.json` (`npm install --package-lock-only`), or adapt the Dockerfile to your package manager.

**Native modules.** Password hashing uses `@node-rs/argon2`. npm installs the matching prebuilt binary as an optional platform package, which covers:
- Linux on glibc and on musl, so the template's Alpine image works, on x64 and arm64;
- macOS;
- Windows.

No compiler, Python or install script is needed, which is why `npm ci --ignore-scripts` in `prod-deps` works.
- Install inside the target environment, as the Dockerfile does. Never copy `node_modules` between operating systems or CPU architectures.
- Don't omit optional dependencies.
- On a platform without a prebuild there is no automatic compile fallback: building from source needs a Rust toolchain.

### Environment

Every service receives only the variables listed for it in the compose files; nothing is passed wholesale with `env_file`. The app container, for example, never sees `MYSQL_ROOT_PASSWORD`. **When you add an app variable, add it to the `app` service's `environment:` block too.**

| Variable | Required | Used by | Notes |
|---|---|---|---|
| `SESSION_SECRET` | yes | app | `openssl rand -base64 48` |
| `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD` | yes | db, migrate, app | Long random password. Inside Compose, `MYSQL_HOST` is set to `db` automatically. |
| `MYSQL_ROOT_PASSWORD` | yes | db | Only used to initialise the database container. |
| `DOMAIN` | yes | proxy, app | Public hostname, e.g. `app.example.com`. Its DNS record must point at the server, and ports 80 and 443 must be reachable. |
| `ACME_EMAIL` | yes | proxy | Let's Encrypt account contact. |
| `ALLOWED_ORIGINS` | no | app | Defaults to `https://$DOMAIN`. |
| `SETUP_TOKEN` | recommended | app | Needed for the first-run setup. If empty, the app prints a one-time token to stderr. |
| `OTP_ENCRYPTION_KEY` | recommended | app | `openssl rand -hex 32`. Keep it stable and backed up. |
| `TOTP_ISSUER`, `LOG_LEVEL`, `SMTP_*` | no | app | See the [variable reference](../packages/stack/README.md#environment-variables). |
| `COMPOSE_FILE` | no | Compose | `docker-compose.yml:docker-compose.prod.yml` on the server. |

`create-toto-app` generates `SESSION_SECRET`, `SETUP_TOKEN`, `OTP_ENCRYPTION_KEY` and both database passwords into `.env`. **Generate fresh values for production**; don't reuse your development `.env`.

The app container sets `NODE_ENV=production`, `PORT=3000` and `TRUST_PROXY=1` (exactly one proxy hop: Traefik).

## First deployment

1. Point the DNS record for `DOMAIN` at the server, and open ports 80 and 443.
2. Copy the project to the server, and create `.env` with the variables above. Restrict its permissions: `chmod 600 .env`.
3. Start everything:

   ```bash
   docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
   ```

   Compose builds the images, waits for the database to be healthy, runs the migrations, starts the app once they succeed, and starts Traefik. If the database never becomes healthy, startup fails with `dependency failed to start: container …-db is unhealthy` instead of waiting forever. Check progress with `docker compose ps` and `docker compose logs migrate app`.
4. Open `https://<DOMAIN>/login` and create the owner account. You need the `SETUP_TOKEN` from `.env`; if you left it empty, the app printed a one-time token to stderr: `docker compose logs app | grep -A2 "setup token:"`.
5. Complete the setup immediately: until an owner exists, anyone with the token can claim the instance.

## Updating

```bash
git pull   # or copy the new version
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

The `migrate` service runs again and applies new migrations before the new app container starts. Read the [upgrading guide](upgrading.md) before bumping `toto-stack` across a minor version.

**Rollback.** Prisma migrations only go forward. To roll back a release that changed the schema, restore a backup, or write a new migration that reverts the change.

## Operations

- **Logs:** `docker compose logs -f app` shows JSON lines with `requestId`. Traefik's access log is in `./logs/access.log`; rotate it (for example with logrotate).
- **Health:** `GET /api/health` returns 200 `{"status":"ok","db":"ok",…}` or 503 when the database is unreachable. The container `HEALTHCHECK` and external monitors use it. `GET /api/status` (one of the app's own routes in `server/routes`) is a liveness check that doesn't touch the database.
- **Backups:**
  - Back up the database volume regularly, for example with `docker compose exec db sh -c 'mariadb-dump -uroot -p"$MARIADB_ROOT_PASSWORD" --single-transaction "$MARIADB_DATABASE"' > backup.sql` (the variables expand inside the container).
  - Back up `.env` separately. Without `OTP_ENCRYPTION_KEY`, an encrypted backup can't be used for MFA logins.
- **Shutdown:** `docker compose stop` sends `SIGTERM`. The template's server uses `shutdown.handleSignals`: it drains in-flight requests (up to 10 s), stops cron jobs (up to 10 s), disconnects Prisma in `onShutdown` and exits with code 0.
  - The template sets `stop_grace_period: 30s` on `app`. Docker's default of 10 s would SIGKILL a server that is still draining. The stack force-exits at the latest `shutdown.timeoutMs` + 5 s after the signal, after up to `timeoutMs` of draining plus up to `timeoutMs` for cron jobs. **If you raise `shutdown.timeoutMs`, raise `stop_grace_period` with it.**
- **Memory:** each running password hash uses `security.passwordHashing.memoryCost` (19 MiB by default), so budget about `concurrency × memoryCost` (≈ 38 MiB) on top of the app's normal usage.
- **Scaling:** before you run more than one `app` replica, read [Running several instances](security.md#running-several-instances). Rate limits and cron jobs are per instance by default.

## The Docker socket

Traefik discovers the app through container labels, which requires mounting `/var/run/docker.sock` (read-only) into the `proxy` container.

**Read access to the Docker socket is effectively root on the host:** it exposes every container's configuration, environment and secrets. Mitigations:
- Keep the proxy image current. It is pinned, and Dependabot proposes updates for the Compose images and the Node base image.
- Don't expose Traefik's dashboard or API; the template doesn't enable them.
- Or put a socket proxy that allows only the read endpoints Traefik needs (for example `tecnativa/docker-socket-proxy`) between Traefik and the socket.
- Or use Traefik's file provider instead of the Docker provider.

## Database users

The `migrate` service and the app both connect as `MYSQL_USER`. That user owns the app database: the MariaDB image grants it all privileges on `MYSQL_DATABASE` only, and no global privileges.

A stricter setup uses a separate user for the app with only `SELECT, INSERT, UPDATE, DELETE`. Creating that user needs an init script; the template doesn't include one.

In development only, `docker/db-init-dev` additionally lets `MYSQL_USER` create Prisma's shadow databases (`prisma_migrate_shadow_db_%`) so that `prisma migrate dev` works. Production never mounts it.

## Without Docker

1. `npm ci && npm run build`. This produces `dist/server.js` and `dist/public`.
2. Set the production environment (see the table above, plus `MYSQL_HOST` and `MYSQL_PORT`), then run `npm run db:deploy` (`prisma migrate deploy`) with the Prisma CLI available.
3. Run `node dist/server.js` under a process manager (systemd, for example) that restarts it and sends `SIGTERM` on stop.
4. Put a TLS-terminating proxy in front, set `TRUST_PROXY=1`, and enable compression there.
